## Proposed narrow architecture

Immediate durable browser state -> UID/device-stamped operation -> stable-key debounce -> bounded foreground retry -> confirmed success acknowledgement. Preserve raw historical stores, payloads and both Notes backups. New personal views must not expose another UID, and old asynchronous responses must not repaint/write into a new UID. Local deletion markers must prevent restore resurrection. Queue revisions must prevent an old success from acknowledging a newer edit; independent atomic record keys avoid array append loss. Use Web Locks when available for cross-tab drains, a bounded renewable lease otherwise, and idempotent operations only. Unknown legacy ownership/ambiguous conflicts stay stored and reported, not guessed.

Online note conflict checking uses existing GET / updated_at evidence; conditional updates may be used only when the server response proves success. No new last-write-wins protocol or guessed server RPC. Simultaneously differing text must be preserved, with pending conflict state rather than automatic destructive overwrite. School and authorization never become locally authoritative.

## Retention

Never prune notes, user-created content, tombstones, pending/conflicted operations, School work or offline downloads. Existing bounded Wave 1 analytics retention remains. Public catalog TTL and in-memory render/search indexes are rebuildable; no cache clear/backfill is needed. Future Notes consolidation is documentation only.

## Validation plan

Real-source VM reconciliation tests and full-app isolated browser tests, FA/EN/HR and reload/offline/account-switch/failure/duplicate events. Re-run identical Wave 1 benchmark against exact d291 archive and measure repeated note/progress/saved edits separately. Full canonical develop checks plus exact pushed-head CI; no release workflow/deploy. Mock backend evidence does not certify native OS process lifetime, actual billing, physical-device performance or unseen live schema.
