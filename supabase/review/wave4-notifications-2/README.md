## Idempotency / failure semantics

Business delivery identity = type + source UUID + recipient UID + channel + business revision + subscription for Push. Inbox uses account once, independent of device/language; Push once per verified device. Provider UUID is deterministic SHA256-derived UUID from that logical key. Manual request UUID is stable from Preview through Confirm/Execute; immutable request/recipient snapshot and ten-minute preview token bind it to server actor. Edits invalidate preview. Concurrent execution uses durable UNIQUE claim INSERT ON CONFLICT DO NOTHING; existing claim state is returned, never released/deleted. Separate channels avoid duplicate Inbox when Push result is unknown. Repeated event/HTTP trigger, double Execute and same approved retry create zero extra sends/rows in fixtures.

`recorded` = Inbox insertion; `accepted` = provider ID accepted, NOT device receipt. `no_subscription`, `revoked`, `unknown`, `partial`, `unavailable` are explicit. Provider timeout/network ambiguity retains claim **unknown**; no automatic/manual blind resend with a new identity. Operator must inspect same logical delivery/provider idempotency receipt first. Future bounded retry may reuse the SAME key only after a definitive non-acceptance is proven; unknown must stay quarantined. Inbox unknown can be reconciled against existing dedupe_key before a reviewed same-row upsert. No cleanup/delete of historical claims/rows. Existing receipt/read/delete timestamps and Wave2 queues are untouched.

## Account/provider security and activation gates

v364 remains sole Web/native binding owner: event-driven serialized login/logout/tag/language operations; UID+JWT/current-signature fences after every await; an old A login cannot publish/tag B and is repaired by logout/current B login. In default client mode existing UID API remains compatible. Logout clears provider association/role hints, not user data. Backend-enabled mode additionally requires a server-signed identity token and provider-verified owned subscription. Registry update never trusts a submitted UID; inactive update may revoke only current Auth UID's record. Fresh provider View User by external_id verifies subscription membership immediately before Push. Tags never authorize server audiences.

Before enabling backend flag, explicitly configure/test **OneSignal identity verification** against the actual Web/native SDK versions and validate proposed HS256 token (`identity.external_id`, issuer/app ID, five-minute expiry) and provider View User response shape. No unsigned fallback when flag=true. Provider callback/expiry/renewal behavior and native SDK support require physical/integration acceptance. A provider request already accepted before logout/revocation cannot be recalled; generic lock-screen copy contains no private detail, and tap is fenced by current UID/permission. No promise that OS suppresses an already-queued notification.

Intentional language change is debounced/deduplicated, owner-captured and backend-gated; pageshow/focus/render do NOT mark a language preference write. Token refresh/same UID does not recreate provider subscriptions. Multiple devices remain independent. Native permission is requested only from existing explicit Enable buttons; no arbitrary first-button gesture, recurring prompts or background polling.
