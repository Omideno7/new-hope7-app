## Analytics ingestion proposal and security prerequisite

Legacy `nh7_track_app_section_v222`, `nh7_track_content_v223`, `nh7_track_audio_session_v222` are already no-ops in captured migration 20261003073335. Their old per-event callers must not be re-enabled. Existing Admin report v223 expects daily app/content rows and audio session summaries. Full current table definitions, unique constraints, ownership columns and RLS are not captured; therefore runnable write SQL guessing those contracts would be unsafe.

The client now preserves bounded UID-scoped local summaries without any analytics network request: UTC daily/language buckets, at most 400 records per owner, 30-day retention, no free-form text and no cross-owner audio-session accumulation. Only these newly introduced noncritical summary records rotate; notes/progress/downloads and all cloud records are untouched. A separately approved batch RPC should accept cumulative daily/session totals in batches of <=50. Derive the owner only from auth.uid(), never trust email/listener_key from payload. Reject anonymous requests. Validate identifiers, dates, language, duration caps and maximum payload bytes. Map UID to the existing report listener key server-side, preserving report semantics. Use an idempotency key (UID, client instance, day, section/content/session) and monotonic cumulative counters: retries must not add the same delta twice. Store at most daily aggregates and session summaries, not keystrokes, notes, profile content, raw events or media files.

Expected benefit: one small foreground/session/background batch can replace hundreds of per-event requests while preserving active users, section/content opens, listened duration and completion reports. This is feasible; analytics deletion is not recommended. Cloud ingestion/report freshness remains deferred until source metadata verification and explicit backend approval. The client keeps unsent summaries rather than falsely acknowledging them through the retired no-op RPCs.

Activation prerequisites: read-only schema/RLS verification, exact proposed function source with auth.uid()/idempotency checks, mixed anonymous/normal/admin and cross-UID test matrix, report reconciliation, payload validation, EXPLAIN and staging load test. Then explicit Production approval. No automatic probe or retry against a nonexistent analytics endpoint in Wave 1.

Rollback: disable the future batch capability first, leaving local unsent summaries intact; restore only the previous approved function definition/EXECUTE grants. Never drop/truncate existing report tables or overwrite rows. Preserve original client queues and notes. Any candidate SQL must include a schema-specific forward/rollback pair after metadata is known.

## Notes consolidation proposal

`user_notes` is keyed by (device_id, note_key) and supports device-bound/legacy compatibility. `nh7_account_notes` is keyed by (user_email, note_key) and is the current account-restore source. Explicit writes/deletes currently target both; School drafts/Bible marks have their own pathways. Keep both cloud backups during this wave. Their combined ~5.3 MB is <0.1% of the reported 6.8 GB Storage; replacing them will not address media egress.

Future consolidation requires read-only UID/email/device coverage counts and conflict inventory, a UID-keyed canonical adapter, additive dual-read/dual-write transition, reconciliation preserving both conflicting texts/timestamps, and account switch/offline/legacy rollback tests. Do not migrate/backfill/delete records automatically. Rollback switches readers to existing tables while preserving both sets and any newly queued edits. Data ownership must be server-enforced, not inferred solely from local cache.

## Wave 2 read-only contract audit and exact minimum acceptance contract

Evidence checked: captured migration `20261003073335_retire_nonessential_telemetry_and_audio_gate_v1.sql` (three tracking bodies return true without writing); `js/nh7-performance-wave1.js` (actual local record fields and caps); Admin analytics v223 integration and `admin-v2.3.5-analytics-core-v237.js` (`state.engagementV223` and `nh7_admin_content_users_v235`, summary/users reporting). `20261010180256_optimize_user_data_rls_initplan_v1.sql` proves account Notes/progress/saved-verse email-JWT policies and UID-owned verse marks, **not** any analytics ingestion policy. No live calls were made. The repository does not establish the complete live analytics table DDL, unique keys, report joins, grants, RLS or transactional ownership mapping. A runnable migration/SQL/RPC definition cannot be safely produced from this evidence.

Minimum future protocol (proposal, no currently callable endpoint):

- Request: authenticated caller JWT; a random persistent client-instance UUID; protocol version; <=50 cumulative records and <=64 KiB serialized payload. Client must not submit an owner UID/email/listener key or free-form text. Anonymous/device-only local buckets stay local unless separately approved; never attribute pre-login events to a signed-in user.
- Record allowlist exactly matches current summaries: UTC `day`, FA/EN/HR `language`, approved `kind` (`app`, `content:<approved type>`, `audio:sermon|school|audio_bible`), canonical `id` (1–120 restricted ASCII characters), nonnegative integer `opens`, finite nonnegative `seconds`, boolean `completed`; audio additionally canonical `media_id`, finite nonnegative `duration_seconds`. Approved server registry resolves content labels, never accepts client note/profile/media URLs/titles. Validate UTC dates within the established 30-day retention, counters/duration against server-approved sensible maxima, per-UID rate and payload caps. Exact numerical maxima need measured approved report/usage semantics, not guessed SQL constants.
- Ownership and security: derive UID only from `auth.uid()` with mandatory non-null check; map existing account/report identity internally. Authenticated-only EXECUTE, explicit secure search_path, table ownership/RLS/grants proven before activation, no arbitrary target-table or content-field parameter. Admin reporting remains server-gated; another UID cannot write/read another user's aggregates.
- Required uniqueness: `(auth UID, client instance, UTC day, language, kind, record id)`. For audio, session id is the current `id`; content id is `media_id`. Upsert cumulative counters using monotonic maxima per unique client record and completion OR. Reports sum independent client records but count users by server-resolved UID. Do not add retry deltas, and do not count one session twice. One transaction validates/updates <=50 items; reject the batch on invalid ownership/shape.
- Response: actual committed result per stable record key/revision with accepted cumulative counters and protocol version. Only acknowledged matching revisions may leave a future pending upload queue; newer counters remain pending. An old no-op `true` is not an acknowledgement. Timeout/duplicate/reordered submissions must converge identically. Server clock/metadata must prevent a client timestamp from controlling authorization.
- Before activation: capture exact current table/index/constraint/policy/grant/function definitions and report readers; prove unique key and UID mapping; run anonymous/normal/admin/cross-UID, duplicate/reordered/partial-failure, two-device and report-total reconciliation tests; EXPLAIN safe reads and approved staging load tests. Supply schema-specific forward/rollback sources for explicit approval only. No batch RPC is deployed or raw-event caller re-enabled in Wave 2.

Rollback requirement remains additive: turn off client capability and future function EXECUTE first, retain existing tables and unsent local aggregates, restore exact reviewed function/grants. No delete/backfill/cleanup of user records. Local 400-record/30-day analytics bounds remain unchanged; pending personal sync, conflicts, tombstones, notes and downloads have **no automatic pruning**. New outbox records disappear only on verified success or equivalent stable-key replacement after the latest durable intent is stored.
